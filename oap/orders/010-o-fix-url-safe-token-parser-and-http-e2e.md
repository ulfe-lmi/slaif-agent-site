## Verified root cause

`format_session_token` and `format_csrf_token` use unpadded URL-safe Base64,
whose valid alphabet contains `_`. `parse_session_token()` calls unrestricted
`split("_")` even though a valid token is:

```text
sas2_session_<32 lowercase hex>_<43 URL-safe Base64 characters>
```

`parse_csrf_token()` has the same defect for:

```text
sas2_csrf_<43 URL-safe Base64 characters>
```

When the encoded secret contains `_`, splitting creates extra fields and rejects
a credential generated by the product itself. The temporary actual-service
ASGI test in `010-n` exposed this honestly and was not committed as passing.
